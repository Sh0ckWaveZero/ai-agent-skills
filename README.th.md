ชุดสกิลที่นำกลับมาใช้ได้สำหรับ AI agent ครอบคลุมการพัฒนาและตรวจสอบโค้ด งาน Git การสร้างและรีวิว GitLab MR การวางแผนและสรุปงาน Jira รวมถึงฟอร์ม React

## เริ่มใช้งาน

1. ติดตั้งชุดสกิลด้วยคำสั่งต่อไปนี้

   ```bash
   npx skills add https://github.com/Sh0ckWaveZero/ai-agent-skills.git
   ```

2. เริ่มเซสชันของ agent ใหม่ เพื่อให้ค้นพบสกิลที่ติดตั้ง
3. เรียกชื่อสกิลพร้อมงานที่ต้องการ หรืออธิบายงานให้ agent เลือกสกิลที่รองรับการเรียกอัตโนมัติ

แต่ละสกิลมีขั้นตอนทำงานของตัวเอง งาน GitLab และ Jira ต้องมี CLI หรือ connector ที่เกี่ยวข้อง พร้อมการยืนยันตัวตนและสิทธิ์เข้าถึงโครงการ

### ความหมายของวิธีเรียก

- **model** — agent สามารถเลือกใช้เมื่อคำขอตรงกับหน้าที่ของสกิล ทั้งนี้ขึ้นกับการค้นพบสกิลและการตั้งค่าของโปรแกรมที่ใช้
- **user** — ผู้ใช้เรียกสกิลโดยตรง เช่น `/<skill-name>` ในโปรแกรมที่รองรับ slash command หรือระบุชื่อสกิลในคำขอ metadata กำหนดให้เรียกโดยผู้ใช้ ส่วนการบังคับใช้ขึ้นกับการรองรับของโปรแกรม

## วิธีใช้งาน

### Engineering mode

อ่าน [คู่มือ Engineering Mode แบบละเอียด](skills/engineering/engineering-mode/README.th.md) สำหรับการออกแบบ ขั้นตอนทำงาน ตัวอย่าง และข้อจำกัดของการตรวจสอบ

ใช้ [`engineering-mode`](skills/engineering/engineering-mode/SKILL.md) เมื่อต้องพัฒนาฟีเจอร์ แก้บั๊ก refactor ตรวจประสิทธิภาพ หรือยืนยันผลบน UI หลังติดตั้งและโปรแกรมค้นพบสกิลแล้ว ให้ระบุชื่อสกิลพร้อมผลลัพธ์ที่ต้องการ

โปรแกรมที่รองรับ slash command:

```text
/engineering-mode แก้บั๊กที่กดบันทึกแล้วข้อมูลหาย
```

ใน Codex ใช้ `$engineering-mode` หรือระบุชื่อสกิลในคำขอ:

```text
ใช้ $engineering-mode เพิ่มฟีเจอร์ค้นหา โดยอ้างอิง Jira PROJ-1234
```

| ตัวอย่างคำขอ | สิ่งที่สกิลจะทำ |
|---|---|
| `ใช้ engineering-mode refactor ส่วนนี้ โดยคงพฤติกรรมเดิม` | ตรวจจุดที่เรียกใช้ ปรับโครงสร้าง และตรวจว่าพฤติกรรมยังตรงกับเดิม |
| `ใช้ engineering-mode หาสาเหตุที่หน้าโหลดช้า แล้วแก้พร้อมวัดผล` | วัดค่าก่อนแก้ หาจุดที่ทำให้ช้า และเปรียบเทียบผลหลังแก้ |
| `ใช้ engineering-mode ตรวจและแก้ layout หน้านี้ให้ตรงกับภาพอ้างอิง` | จำลองสถานะที่เห็นและตรวจ UI หลังแก้เมื่อเข้าถึง browser ได้ |
| `ใช้ engineering-mode วางแผนแก้เรื่องนี้ก่อน ยังไม่ต้องแก้โค้ด` | จัดทำแผนจากข้อมูลที่ตรวจสอบได้ |

สกิลจะเลือกขั้นตอนตามประเภทงาน ตรวจโค้ดและข้อกำหนดที่เกี่ยวข้อง ทำงานตามคำขอ แล้วรายงานหลักฐานการตรวจสอบและข้อจำกัด โดยใช้กับงานนั้นและการติดตามงานต่อเนื่อง หากต้องการ push เปิด PR/MR merge หรือ deploy ให้ระบุการกระทำนั้นในคำขอด้วย การเรียกสกิลเพียงอย่างเดียวไม่ได้อนุญาตให้เผยแพร่งาน

หากต้องการลองฉบับในเครื่องก่อนติดตั้งหรือเผยแพร่ ให้ agent อ่านไฟล์โดยตรงจาก workspace ของ repo นี้:

```text
อ่าน skills/engineering/engineering-mode/SKILL.md
แล้วใช้ขั้นตอนของสกิลนี้ทำงาน: <งานที่ต้องการ>
```

ถ้าอยู่ใน workspace อื่น ให้ระบุ path จริงของไฟล์ การเรียกด้วยชื่อสกิลต้องติดตั้งฉบับที่มีสกิลนี้และเริ่มเซสชันใหม่ ฉบับที่เผยแพร่ก่อนเพิ่มสกิลจะยังไม่มีไฟล์ที่เพิ่งสร้างในเครื่อง

### สกิลที่ผู้ใช้เรียกโดยตรง

ใช้ `/<skill-name>` ในโปรแกรมที่รองรับ หรือระบุชื่อสกิลในคำขอ ตัวอย่างภาษาธรรมชาติในตารางสื่อถึงงานที่ต้องการ ส่วนการเลือกสกิลอัตโนมัติขึ้นกับโปรแกรมและการตั้งค่า

| คำขอ | ผลที่ได้ |
|---|---|
| `/glab-mr` หรือ `ใช้ glab-mr สร้าง MR` | ตรวจขอบเขตและแนวทางของ repo แล้ว commit/push และสร้างหรืออัปเดต MR เมื่ออยู่ในคำขอ |
| `/glab-mr-review` พร้อม URL หรือ IID ของ MR | รีวิว diff และเผยแพร่สรุปหรือคอมเมนต์ตามบรรทัดเมื่อได้รับคำสั่ง |
| `/jira-bug PROJ-123` | เปรียบเทียบโค้ดในขอบเขตที่เลือกกับบั๊ก ร่างสรุป และโพสต์เมื่อได้รับคำสั่ง |
| `/jira-cr PROJ-123` | เชื่อม acceptance criteria กับโค้ดและหลักฐานการตรวจสอบ แล้วโพสต์เมื่อได้รับคำสั่ง |
| `/jira-plan PROJ-123` | อ่าน ticket แล้วจัดทำแผนและรายการงาน ลงมือพัฒนาต่อเมื่อคำขอครอบคลุมการพัฒนาด้วย |

### สกิลที่ agent เลือกใช้ได้

| สกิล | ใช้เมื่อ |
|---|---|
| `engineering-mode` | พัฒนา วิเคราะห์บั๊ก refactor หรือตรวจงานที่มีหลายขั้นตอน; เรียกโดยตรงได้เช่นกัน |
| `git-flow` | สร้าง branch เขียน commit ทำ release tag หรือเลือก branch เป้าหมาย |
| `git-cherry-pick` | cherry-pick ทำ backport หรือย้าย commit ของงานที่เลือกระหว่าง branch |
| `react-hook-form-zod` | สร้างฟอร์ม เพิ่ม validation หรือแก้ปัญหา resolver และสถานะ field |
| `jira-story-point` | ประเมินขนาดงานหรือแนะนำ Story Points ของ Jira ticket |
| `jira-mcp` | ร่างหรือสร้าง Jira ticket จากข้อกำหนดหรือบันทึกงาน |

ตัวอย่าง:

```text
ช่วยสร้าง branch ใหม่สำหรับ PROJ-456 เรื่อง login throttling หน่อย
→ git-flow ตรวจแนวทางของ repo และ refs ก่อนเลือกชื่อ branch และฐานที่ใช้
```

```text
เพิ่มฟอร์มรีเซ็ตรหัสผ่านด้วย Zod validation
→ react-hook-form-zod ตรวจรูปแบบข้อมูลของฟอร์มและ validation ฝั่ง client/server
```

## โครงสร้าง repo

```text
skills/
├── engineering/
│   └── engineering-mode/    # ขั้นตอนพัฒนาและตรวจสอบผล
├── git/
│   ├── git-flow/            # branch, commit, เป้าหมาย MR และ tag
│   ├── git-cherry-pick/     # ย้าย commit ตามขอบเขตที่เลือก
│   ├── glab-mr/             # เตรียมหรือสร้าง GitLab MR
│   └── glab-mr-review/      # รีวิว MR และคอมเมนต์ตามบรรทัด
├── jira/
│   ├── jira-bug/            # สรุป Bug CR
│   ├── jira-cr/             # สรุป Change Request
│   ├── jira-plan/           # วางแผนพัฒนา
│   ├── jira-story-point/    # ประเมิน Story Points

└── frontend/

```

แต่ละสกิลอยู่ในโฟลเดอร์ของตัวเองและมี `SKILL.md` คำแนะนำเฉพาะกรณีอยู่ใน `references/` ที่ลิงก์จากสกิล ส่วนโค้ดตั้งต้นอยู่ใน `templates/` เก็บไฟล์ที่จำเป็นไว้ภายในสกิลเพื่อให้ติดตั้งแยกได้

## การติดตั้ง

ติดตั้งชุดสกิลด้วยคำสั่ง:

```bash
npx skills add https://github.com/Sh0ckWaveZero/ai-agent-skills.git
```

เริ่มเซสชันของ agent ใหม่หลังติดตั้ง รายการที่ใช้ได้ขึ้นกับฉบับของ repo ที่ติดตั้ง

## การเขียนรายละเอียด MR

`glab-mr` ใช้ template ของ repo และ [แนวทางเขียนรายละเอียด MR](skills/git/glab-mr/references/mr-description.md) เพื่ออธิบายปัญหา พฤติกรรมหลังแก้ แนวทางที่ใช้ และผลตรวจสอบจริง เพิ่มจุดที่อยากให้ผู้รีวิวดู ภาพ ตัวอย่าง API หรือรายละเอียด deployment เมื่อมีประโยชน์ งานเล็กควรอธิบายให้กระชับ และรักษาข้อมูลที่คนเขียนไว้เมื่ออัปเดต MR

## มาตรฐานรีวิวโค้ด

`glab-mr-review` มี [มาตรฐานรีวิว](skills/git/glab-mr-review/references/review-standard.md), [รูปแบบคอมเมนต์และความหมายของ emoji](skills/git/glab-mr-review/references/comment-format.md) และ [กรณีตัวอย่างสำหรับเทียบผลรีวิว](skills/git/glab-mr-review/references/review-cases.md) โดยแยกระดับความรุนแรง สถานะที่ขวางการผ่านรีวิว หลักฐาน และข้อสรุปออกจากกัน การรีวิวซ้ำจะติดตามข้อค้นพบเดิมและตรวจการเปลี่ยนแปลงใหม่ สามารถงด emoji ได้หาก repo ใช้ข้อความล้วน

## การตรวจสอบสกิล

รันคำสั่งจาก root ของ repo:

```bash
python3 tests/validate_skills.py
git diff --check
```

ใช้ [กรณีตรวจขั้นตอนทำงาน](tests/skill-workflows.md) ทบทวนการตัดสินใจหลังแก้สกิล และดู [บันทึกผลตรวจสอบ](tests/validation-results.md) สำหรับผลที่รันจริงและข้อจำกัด กรณีเหล่านี้ใช้ตรวจคำแนะนำของสกิล ยังไม่ใช่หลักฐานว่าได้รันงานจริงบน GitLab/Jira

## การสร้างสกิลใหม่

เพิ่มโฟลเดอร์ใต้ `skills/<หมวด>/<ชื่อสกิล>/` พร้อมไฟล์ `SKILL.md` ตัวตรวจสอบของ repo ค้นหาสกิลที่ความลึกสองระดับนี้ เช่น:

```markdown
---
name: my-skill
description: อธิบายหน้าที่ของสกิลและเงื่อนไขที่ควรใช้
disable-model-invocation: true
---

# ชื่อสกิล

## ใช้เมื่อ

ผู้ใช้เรียก `/my-skill` หรือระบุชื่อสกิลพร้อมงานที่ต้องการ

## ขั้นตอนทำงาน

1. ขั้นตอนแรก
2. ขั้นตอนถัดไป
```

### ฟิลด์ใน frontmatter

| ฟิลด์ | หน้าที่ |
|---|---|
| `name` | ชื่อสกิล ต้องตรงกับชื่อโฟลเดอร์ |
| `description` | บอกหน้าที่และเงื่อนไขที่ควรใช้ เพื่อให้ agent เลือกได้ตรงงาน |
| `disable-model-invocation` | ตั้งเป็น `true` สำหรับสกิลที่ต้องเรียกโดยผู้ใช้; ละไว้สำหรับสกิลที่ agent เลือกใช้ได้ |

เพิ่มสกิลในตารางของ README ทั้งสองภาษา แล้วรันการตรวจสอบโครงสร้าง เอกสารแนะนำการใช้งานนี้มีสองภาษา ส่วนไฟล์คำสั่งของสกิลและเอกสารอ้างอิงยังใช้ภาษาตามไฟล์ต้นฉบับ
